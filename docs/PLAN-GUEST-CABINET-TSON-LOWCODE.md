# eKhizmat — план дизайн-прототипа: «Гость», кабинет, ЦОН и Low Code

Статус: handoff для product/design/frontend/QA  
Формат результата: интерактивный plain HTML/CSS/JS demo  
Дата: 28 июля 2026  
Основание: аудит текущих экранов Citizen, ЦОН, Ведомство, Admin и общей дизайн-системы

## 1. Что именно мы делаем

Нужно расширить существующий демонстрационный проект так, чтобы новые идеи можно было:

1. показать руководству и заказчикам как цельный продукт;
2. проверить на понятность и визуальную согласованность;
3. передать команде разработки как живой UX/UI-референс.

Это **не production-разработка**. Все новые действия работают как управляемая имитация в браузере: пользователь нажимает кнопки, видит состояния, ошибки, подтверждения и результат, но настоящие сервисы, API и права доступа не подключаются.

### В результат входят

- аудитория «Гость» рядом с ФЛ и ЮЛ во всех релевантных интерфейсах;
- новый обзор заявлений по категориям в личном кабинете;
- упрощённый раздел «Семья» только для несовершеннолетних детей;
- mock-биометрия и включённая по умолчанию 2FA в «Безопасности»;
- операционный и управленческий дашборды ЦОН;
- mock-процесс создания услуги ведомством, stage-preview, review и публикации администратором;
- адаптация под desktop/mobile, RU/TG, light/dark и текущую дизайн-систему;
- понятные demo-сценарии и автоматические проверки ключевых переходов.

### В результат не входят

- настоящая Face ID, камера, WebAuthn/passkeys или хранение биометрии;
- backend, база данных, API, серверная авторизация и реальные роли;
- реальная отправка SMS, push, e-mail или 2FA-кода;
- реальные stage/prod environments и deployment workflow;
- настоящие аналитические данные ЦОН и подключение BI;
- полноценный production security-аудит;
- юридическое утверждение списка услуг, доступных гостю.

## 2. Что уже есть и что переиспользуем

Проект уже разделён на четыре демонстрационные среды:

| Среда | Маршрут | Что используем как основу |
| --- | --- | --- |
| Citizen | `/citizen/` | каталог, карточки категорий, кабинет, переключатель ФЛ/ЮЛ |

`design-system/` остаётся единственным источником токенов, базовых компонентов и поведения. Новые экраны не должны создавать вторую визуальную систему.

Особенно важно переиспользовать уже существующие решения:

- карточки категорий главной страницы Citizen — для группировки заявлений;
- Face ID-сцену ЦОН — для mock-биометрии в кабинете;
- metric cards и таблицы отчёта Ведомства — для дашбордов ЦОН;
- текущий конструктор Admin, sandbox и кнопки согласования — для Low Code workflow;
- общие dialog, toast, menu, focus и platform switcher из дизайн-системы.

## 3. Правила построения demo

### 3.1 Предсказуемое поведение

Demo должен одинаково работать на каждой презентации. Все данные фиксированы в mock-fixtures. Изменения сохраняются только локально в браузере или в памяти страницы.

Добавить одну служебную команду **«Сбросить demo»**, которая возвращает:

- пользователя к ФЛ;
- 2FA во включённое состояние;
- биометрию в состояние «Не настроена»;
- mock-заявления к исходному набору;
- Low Code-услугу к статусу «Черновик»;
- выбранную роль ЦОН к оператору.

Хранилище, если оно нужно между страницами, использовать только под namespace `ekh.demo.*`. Никакие чувствительные данные не имитировать и не хранить.

### 3.2 Честная маркировка

На внутренних дашбордах и workflow-экранах показать небольшой badge **«Демо-данные»**. Не ставить его на каждом компоненте — достаточно один раз в header или рядом с фильтрами.

### 3.3 Один и тот же объект выглядит одинаково

- «Гость» везде использует один label, icon и цвет badge;
- статусы review в реестре, конструкторе и очереди согласования совпадают;
- категория заявления повторяет icon и название каталога Citizen;
- stage всегда обозначается одним environment badge;
- одни и те же статусы заявления используют одинаковые цвета и подписи.

## 5. Workstream A — «Гость» на всех платформах

### 5.1 Единая модель аудитории

В интерфейсе использовать три базовых варианта:

- **Физическое лицо**;
- **Юридическое лицо**;
- **Гость**.

В конструкторе услуга может быть доступна одной или нескольким аудиториям. Поэтому там лучше использовать checkbox/multi-select, а не radio. В Citizen это именно переключатель текущего режима, поэтому остаётся single-select.

### 5.2 Citizen: вход в гостевой режим

В существующий переключатель аккаунта добавить третий пункт **«Гость»**.

После выбора гостя:

- avatar заменяется нейтральной guest-иконкой;
- персональное имя не показывается;
- появляется компактная подсказка: «Вы просматриваете услуги без входа»;
- рядом остаётся CTA **«Войти»**;
- каталог перестраивается на guest-fixture;
- личный кабинет не открывается как будто пользователь авторизован;
- при попытке открыть персональную функцию показывается диалог с объяснением и CTA входа.

### 5.3 Гостевой каталог

Для demo не нужно дублировать сотни существующих услуг. Собрать короткий, хорошо контролируемый набор из 6–8 карточек в 3–4 категориях. Финальные названия должен подтвердить product owner; до этого использовать явно демонстрационные примеры:

| Категория | Пример mock-услуги | Что демонстрируем |
| --- | --- | --- |
| ЦОН и запись | Записаться на посещение ЦОН | выбор центра, даты и времени |
| Документы | Проверить готовность документа | номер заявки + результат |
| Консультации | Получить консультацию по услуге | короткая форма обратной связи |
| Обращения | Сообщить о проблеме | тема, описание, контакт |

На карточке услуги показать badge **«Доступно гостю»**. Внутри страницы услуги явно объяснить, какие данные всё равно потребуются для конкретного обращения.

### 5.4 Гостевой mock-flow

Для одной эталонной услуги собрать полный переход:

1. Гость открывает услугу.
2. Видит краткое описание и badge аудитории.
3. Нажимает «Получить услугу».
4. Заполняет 2–4 безопасных поля-заглушки.
5. Подтверждает согласие checkbox.
6. Получает success screen с демонстрационным номером `GST-2026-0042`.

На success screen не обещать, что обращение реально отправлено. Текст: **«Демо-заявка сформирована»**.

### 5.5 Где ещё показать «Гость»

| Место | Изменение |
| --- | --- |
| Admin → новая услуга | добавить «Гость» в блок «Для кого» |
| Admin → реестр | badge и фильтр по аудитории «Гость» |
| Admin → конструктор | guest-preview и audience condition |
| Admin → шаблоны | минимум один guest-ready template |
| Ведомство → карточка заявления | audience badge, если заявка гостевая |
| ЦОН → каталог услуги | guest badge в метаданных услуги |
| ЦОН → идентификация | вариант «Продолжить как гость» только у разрешённых mock-услуг |

Не нужно искусственно добавлять «Гость» туда, где экран относится только к авторизованному кабинету. Вместо этого показывать объясняющее empty/locked state.

### 5.6 Acceptance criteria

- во всех местах, где сейчас пользователь выбирает только ФЛ/ЮЛ, есть «Гость»;
- guest mode визуально отличается, но использует те же компоненты;
- минимум одна гостевая услуга проходится от каталога до success screen;
- гость не выглядит авторизованным и не получает ложный личный кабинет;
- после reload/reset demo возвращается в согласованное исходное состояние;
- RU/TG-тексты не ломают layout.

## 6. Workstream B — заявления по категориям в личном кабинете

### 6.1 Новая информационная архитектура

Текущий экран сразу показывает одну подробную карточку заявления. Новый flow должен иметь три уровня:

1. **Категории** — обзор всех тем и количества заявлений.
2. **Список категории** — все заявления выбранной темы.
3. **Детали заявления** — существующий timeline и информация о конкретной заявке.

Навигация:

`Мои заявления → Документы и справки → Заявление №...`

На втором и третьем уровнях обязательно иметь явную кнопку «Назад» и breadcrumb на desktop.

### 6.2 Экран категорий

Переиспользовать визуальный стиль карточек категорий с главной страницы Citizen:

- тот же icon container;
- те же radius, spacing, hover/focus и typography;
- название категории;
- новое значение **«5 заявлений»**;
- необязательная строка «Последнее обновление: сегодня».

Главное правило: число на карточке — это **общее количество заявлений в категории независимо от статуса**. Фильтры статусов на следующем экране не меняют это число.

Предлагаемый mock-набор:

| Категория | Всего | Статусы внутри |
| --- | ---: | --- |
| Документы и справки | 5 | 2 завершено, 2 в работе, 1 отклонено |
| Семья | 3 | 1 завершено, 1 в работе, 1 черновик |
| Транспорт | 3 | 1 завершено, 1 в работе, 1 отклонено |
| Жильё | 2 | 1 завершено, 1 в работе |
| Налоги | 2 | 1 завершено, 1 черновик |
| Социальная поддержка | 1 | 1 в работе |
| **Итого** | **16** | сумма всегда совпадает с карточками |

Показывать только категории, где есть хотя бы одна заявка. Для проверки empty state предусмотреть отдельный demo-переключатель, а не пустые карточки среди реальных.

### 6.3 Список выбранной категории

Header экрана:

- icon и название категории;
- текст «5 заявлений»;
- кнопка назад;
- status chips: «Все», «В работе», «Завершено», «Отклонено», «Черновики».

Каждая строка/карточка заявления содержит:

- название услуги;
- номер заявления;
- дату подачи;
- текущий статус;
- последнее обновление;
- chevron для открытия деталей.

На mobile использовать вертикальные cards, на desktop — компактный list/table hybrid.

### 6.4 Детали заявления

Сохранить существующий подробный tracking card и встроить его третьим уровнем. Добавить только:

- контекст категории;
- кнопку возврата к списку;
- единый status badge;
- mock-действия, если они уже есть в карточке.

### 6.5 Состояния

Нужно собрать и проверить:

- стандартный набор из 16 заявлений;
- категория после фильтра без совпадений;
- полностью пустой кабинет;
- длинное название услуги;
- rejected item с видимой причиной;
- keyboard focus при входе и возврате между уровнями.

### 6.6 Acceptance criteria

- первый экран «Моих заявлений» всегда показывает категории, а не случайную заявку;
- сумма category counts равна количеству fixture-заявлений;
- count не меняется при фильтрации по статусу;
- category → list → detail → back работает без перезагрузки;
- карточки визуально узнаваемо повторяют каталог Citizen;
- mobile, RU/TG, light/dark проверены.

## 7. Workstream C — раздел «Семья»

### 7.1 Что убрать

Из раздела удалить:

- супруга/супругу;
- родителей;
- приглашения родственников;
- любые действия добавления взрослого члена семьи;
- связанные с родителями tabs/empty states в wallet, если они ведут в старый сценарий.

### 7.2 Что оставить

- заголовок «Дети»;
- существующую карточку несовершеннолетнего ребёнка;
- кнопку **«Добавить ребёнка»**;
- empty state, если детей нет;
- просмотр mock-документов ребёнка, если он уже был в интерфейсе.

### 7.3 Mock-добавление ребёнка

Диалог содержит:

- ФИО ребёнка;
- дату рождения;
- номер свидетельства/документа;
- связь с заявителем;
- кнопки «Отмена» и «Добавить».

Поведение:

- пустые обязательные поля подсвечиваются после submit;
- возраст 18+ даёт inline-error: «Можно добавить только несовершеннолетнего ребёнка»;
- корректные данные добавляют новую карточку и показывают toast;
- это только browser-state; настоящая проверка родства не выполняется;
- reset demo удаляет добавленную карточку.

### 7.4 Acceptance criteria

- на экране нет сценариев супруга, родителей или других взрослых;
- единственное add-action относится к ребёнку;
- mock-валидация блокирует дату рождения взрослого;
- success, error и empty states доступны с клавиатуры и понятны без цвета.

## 8. Workstream D — «Безопасность»: 2FA и mock-биометрия

### 8.1 2FA по умолчанию

На исходном demo-state переключатель 2FA всегда включён.

Рядом показать:

- status «Включено»;
- пояснение «Дополнительная проверка при входе»;
- badge или helper text «Включено по умолчанию».

Toggle можно оставить интерактивным для презентации. При выключении показать confirmation dialog. Это только визуальная имитация; SMS/OTP не отправляются.

После **«Сбросить demo»** 2FA снова включена.

### 8.2 Mock-биометрия

В ЦОН уже существует нужный визуальный pattern:

- квадратная рамка лица `.facescan`;
- анимированная scanning line;
- состояние scanning;
- capture dialog в регистрации;
- кнопки «Пропустить» и «Сделать снимок»;
- mock-success после короткой задержки.

Для Citizen не создавать другую «Face ID». Вынести этот pattern в переиспользуемый рецепт дизайн-системы или аккуратно повторно подключить его стили и состояния.

### 8.3 Экран и состояния

Добавить строку **«Биометрия»** под 2FA:

Начальное состояние:

- icon лица;
- status «Не настроена»;
- helper «Быстрый вход на поддерживаемом устройстве»;
- кнопка «Настроить».

После клика:

1. Открывается dialog с тем же Face ID pattern, что в ЦОН.
2. Пользователь нажимает «Начать сканирование».
3. 1.5–2 секунды идёт CSS-анимация.
4. Показывается success-icon и текст «Биометрия настроена».
5. После закрытия строка получает status «Включено» и действие «Удалить».

Дополнительно предусмотреть mock-error через demo control: «Лицо не распознано — попробуйте ещё раз».

### 8.4 Честный microcopy

Нигде не писать, что браузер действительно распознал лицо. В dialog добавить малозаметную подпись **«Демонстрационный режим — камера не используется»**.

### 8.5 Acceptance criteria

- 2FA checked при первом открытии и после reset;
- mock-биометрия имеет idle, scanning, success и error;
- камера и системные разрешения не запрашиваются;
- Citizen и ЦОН визуально используют один Face ID pattern;
- dialog закрывается по Escape, удерживает focus и возвращает его на trigger.

## 9. Workstream E — дашборды ЦОН

### 9.1 Общая идея

Текущий ЦОН уже показывает мини-сводку смены оператора: 47 визитов, среднее время 06:12, 31 завершённая услуга. Это хорошая отправная точка.

Добавить два уровня выше оператора:

1. **Руководитель отделения** — управляет текущей ситуацией одного ЦОН.
2. **Руководство** — смотрит сеть ЦОН, регионы и динамику.

Все графики и числа — фиксированные demo-fixtures. Никакие реальные данные не загружаются.

### 9.2 Demo-переключатель роли

В user menu ЦОН добавить режим:

- Оператор;
- Руководитель отделения;
- Руководство.

Это не настоящие права. Переключатель можно показывать только при `?dev=1` или пометить как **«Роль для demo»**.

### 9.3 Dashboard руководителя отделения

Задача экрана: за 10 секунд ответить, всё ли нормально в конкретном центре прямо сейчас.

Header:

- «ЦОН №3, Душанбе»;
- текущая дата и время;
- badge «Демо-данные»;
- фильтр «Сегодня / Неделя»;
- last updated.

KPI row:

| Метрика | Mock-значение | Контекст |
| --- | ---: | --- |
| Визиты сегодня | 47 | +8% к прошлому дню |
| В очереди сейчас | 12 | 3 ожидают больше 15 минут |
| Среднее ожидание | 06:12 | цель до 10 минут |
| Услуги завершены | 31 | 89% без возврата |
| Окна работают | 8/10 | 1 перерыв, 1 закрыто |

Основные блоки:

- очередь по зонам: документы, регистрация, консультации;
- нагрузка по часам — простой bar/line chart;
- состояние окон и операторов;
- популярные услуги;
- предупреждения: долгое ожидание, закрытое окно, возвраты;
- последние операции/инциденты.

Действия вроде «Открыть окно» или «Назначить оператора» можно показать как disabled/demo-only, если полный flow не нужен.

### 9.4 Dashboard руководства

Задача экрана: быстро сравнить регионы/центры и увидеть проблемные зоны.

Фильтры:

- период;
- регион;
- конкретный ЦОН;
- тип услуги;
- аудитория: ФЛ / ЮЛ / Гость.

Top KPIs:

| --- | ---: |
| Всего визитов | 2 486 |
| Обслужено в SLA | 92,6% |
| Среднее ожидание | 08:14 |
| Активные центры | 42/45 |

Контент:

- динамика визитов и среднего ожидания;
- распределение по регионам;
- top/bottom центров;
- таблица ЦОН с SLA, ожиданием, загрузкой и alert status;

### 9.5 Визуализация

Для demo достаточно CSS и небольших inline SVG. Не подключать тяжёлую charting library, если существующие средства покрывают line/bar/donut.

Обязательные правила:

- chart не является единственным способом прочитать число;
- tooltip доступен с клавиатуры или рядом есть таблица/legend;
- цвет не используется как единственный признак проблемы;
- все значения форматируются одинаково;
- при узком экране KPI становятся горизонтально прокручиваемыми или складываются в 1 колонку без обрезки.

- normal;
- «высокая очередь»;
- пустой период;
- loading skeleton;
- error panel «Не удалось обновить данные».

### 9.7 Acceptance criteria

- из ЦОН можно переключиться в два новых dashboard view;
- supervisor отвечает за один центр, leadership — за сеть;
- числа внутри каждой сцены математически согласованы;
- фильтры меняют mock-сцену или выбранные labels, а не выглядят сломанными;
- есть drill-down от таблицы руководства к конкретному ЦОН;
- экраны используют существующие metric cards, panels, tables и tokens.

## 10. Workstream F — Low Code для ведомств и review workflow

### 10.1 Роли внутри demo

Для презентации нужны три perspective:

| Роль | Может в demo | Не может в demo |
| --- | --- | --- |
| Автор ведомства | создать, редактировать, preview на stage, отправить на review, ответить на комментарий | опубликовать услугу |
| Ревьюер согласующего органа | открыть очередь, комментировать, запросить изменения, отклонить, одобрить | менять форму как автор |
| Администратор портала | проверить одобренную версию и опубликовать | публиковать неодобренную версию |

Это только интерфейсные ограничения. Их нельзя считать настоящей системой доступа.

Если в реальном процессе ревьюер и администратор — одна команда, роли можно объединить позже. Для demo их разделение лучше показывает контрольную точку перед публикацией.

### 10.2 Статусы услуги

Использовать одну цепочку во всех экранах:

`Черновик → На stage → На проверке → Требуются изменения → Повторная проверка → Одобрено → Опубликовано`

Отдельная ветка:

`На проверке → Отклонено`

Для каждого статуса определить один label, badge color и доступные mock-actions.

### 10.3 Автор ведомства: реестр

Добавить demo-role switcher **«Ведомство»**. В этой роли реестр показывает только fixture-услуги своего ведомства и понятный status summary:

- 3 черновика;
- 1 на проверке;
- 1 требует изменений;
- 2 опубликовано ранее.

Primary CTA: **«Создать услугу»**.

На row/card показывать:

- название;
- аудитории ФЛ/ЮЛ/Гость;
- текущую версию;
- environment badge Stage;
- review status;
- дату последнего изменения;
- доступное действие.

### 10.4 Автор ведомства: конструктор

Переиспользовать текущий Admin Builder. Изменения:

- добавить audience «Гость» в service settings;
- добавить preview-switcher ФЛ/ЮЛ/Гость;
- в header явно показать **Stage**;
- заменить доступную автору кнопку «Опубликовать» на disabled action с tooltip: «Публикация доступна после проверки администратору портала»;
- оставить «Сохранить»;
- добавить primary CTA **«Отправить на проверку»**;
- показать version/history panel и comments panel.

Sandbox остаётся визуальным preview текущей формы. Никакого настоящего stage deployment нет.

### 10.5 Отправка на review

После «Отправить на проверку» открыть summary dialog:

- название услуги;
- версия;
- аудитории;
- изменённые разделы;
- checklist автора;
- необязательный комментарий ревьюеру.

После подтверждения:

- status меняется на «На проверке»;
- редактирование становится read-only или показывается предупреждение;
- появляется toast;
- fixture попадает в review queue.

### 10.6 Очередь ревьюера

Новый view внутри Admin:

- tabs «Новые», «Повторно», «Одобрено», «Отклонено»;
- фильтры по ведомству, аудитории и дате;
- карточки/строки услуг;
- badge количества замечаний;
- SLA-label можно показать как demo-индикатор, без реального расчёта.

Эталонный fixture: **«Запись на консультацию по земельным вопросам»**, версия 0.4, аудитории ФЛ + Гость.

### 10.7 Review workspace

Экран делится на:

- preview формы;
- summary метаданных;
- checklist проверки;
- comments panel;
- action bar.

Actions:

- «Добавить комментарий» с привязкой к шагу/полю;
- «Запросить изменения»;
- «Отклонить»;
- «Одобрить».

Для demo достаточно одного заранее подготовленного замечания и возможности добавить ещё одно локально.

Сценарий «Запросить изменения»:

1. Ревьюер пишет: «Уточните формат номера документа».
2. Status становится «Требуются изменения».
3. Автор видит comment badge в реестре и builder.
4. Автор меняет mock-field и отвечает.
5. Нажимает «Отправить повторно».
6. Status становится «Повторная проверка».

### 10.8 Одобрение и публикация

После «Одобрить»:

- status «Одобрено»;
- появляется review summary с именем demo-reviewer и временем;
- кнопка публикации всё ещё недоступна автору ведомства.

В perspective администратора портала:

- одобренная услуга появляется в очереди публикации;
- кнопка **«Опубликовать»** доступна только для status «Одобрено»;
- после клика confirmation dialog показывает version и аудитории;
- финальный status становится «Опубликовано»;
- услуга появляется в mock registry/catalog с badge «Опубликовано».

Если status не «Одобрено», кнопка disabled и объясняет причину.

### 10.9 Acceptance criteria

- автор ведомства может собрать форму и пройти stage-preview;
- «Гость» доступен в settings, preview и registry;
- автор нигде не может mock-опубликовать свою услугу;
- review queue позволяет comment/request changes/reject/approve;
- комментарий виден и ревьюеру, и автору;
- повторная отправка меняет status;
- администратор может опубликовать только одобренную fixture-версию;
- reset demo возвращает workflow к «Черновику».

## 17. Общий Definition of Done

Работа считается готовой к handoff, когда:

- все пять demo-сценариев проходятся без ручного вмешательства в код;
- после reset они повторяются с исходными данными;
- дизайн-система документирует новые shared patterns;
- desktop, tablet и mobile не имеют горизонтальных обрезок;
- light/dark и RU/TG не ломают hierarchy и размеры controls;
- все dialogs имеют focus trap, Escape и возврат focus;
- interactive elements доступны с клавиатуры;
- status не передаётся только цветом;
- `npm test` и design-system checks проходят;
- в интерфейсе нет заявлений о настоящем Face ID, публикации или отправке данных;
- README объясняет, какие действия являются demo-only;
- команда разработки может по экрану определить будущие состояния и переходы, не воспринимая mock как готовую production-архитектуру.

## 18. Главный принцип handoff

Этот build должен отвечать на вопрос **«как продукт должен выглядеть и вести себя»**, а не **«как production-система уже реализована внутри»**.

Поэтому команда тщательно прорабатывает:

- экраны;
- переходы;
- роли и видимые ограничения;
- empty/loading/error/success states;
- wording;
- responsive behavior;
- доступность;
- единообразие дизайн-системы.

А backend, настоящие разрешения, security, публикация, аналитика и биометрическая интеграция остаются отдельным следующим этапом после утверждения demo.
