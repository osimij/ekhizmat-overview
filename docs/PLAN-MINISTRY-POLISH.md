## 0. Характер движения АРМ

АРМ — инструмент, в котором оператор живёт всю смену. Личность движения: **спокойное, мгновенное, официальное**. Отсюда два железных правила:

1. **Частота определяет анимацию.** Что делается 100+ раз в день (фильтры, перерисовка очереди, переключение сегментов) — мгновенно, без переходов. Что случается редко (вход в смену, блокировка, успешное решение) — может быть тёплым.
2. **Никаких bounce и spring.** Государственный продукт не пружинит. Только уверенные ease-out кривые до 300 мс.

Главный диагноз аудита: **входы анимированы, выходы — нет.** Модалки, поповеры и тосты появляются с переходом, а исчезают телепортом (`innerHTML = ''`, `remove()`). Ощущение «дёшево» создаёт именно это: вещи, пропадающие в никуда. Основная масса работ — дать каждому слою симметричный (и чуть более быстрый) выход.

## Фаза 0 — фундамент: токены и линт (~0.5 дня)

Цель: одна система кривых/длительностей, из которой нельзя случайно выпасть.

| Before | After | Why |
| --- | --- | --- |
| В токенах только `--ease` и `--ease-layer` ([motion.css:2](../design-system/tokens/motion.css)) | Добавить `--ease-out: cubic-bezier(.23, 1, .32, 1)` и `--t-exit: 160ms` (в reduce-блоке тоже обнулить `--t-exit`) | Сильная ease-out-кривая уже используется в коде, но «вручную»; выходы слоёв должны быть быстрее входов — нужен отдельный токен |
| `transition: transform 180ms cubic-bezier(.23,1,.32,1)` — сырая кривая в floating label ([app.css:2199](../apps/ministry/app.css)) | `transition: transform var(--t-step) var(--ease-out)` | Кривые живут только в токенах; дубли неизбежно разъезжаются |
| `setTimeout(finish, 160)` — магическое число в закрытии диалога ([dialog.js:85](../design-system/js/dialog.js)) | Читать длительность из `--t-exit` (`getComputedStyle`) либо ждать `transitionend` с таймаут-страховкой | Сейчас CSS ведёт выход 200 мс, а JS обрывает DOM на 160-й — хвост анимации срезается |
| Линт не ловит сырые кривые (`qa/design-lint.mjs` запрещает только `transition: all` и сырые цвета) | Добавить правило: `cubic-bezier(` вне `design-system/tokens/` — ошибка | Автоматика вместо ревью-памяти; тот же приём, что уже принят для цветов |

Приёмка: `npm run lint:design-system` падает на тестовом файле с сырой кривой; в `apps/` не остаётся ни одного `cubic-bezier`.

## Фаза 1 — слои: у выхода тоже есть анимация (~1 день) — самый ощутимый пункт плана

Сейчас модал открывается двумя конкурирующими механизмами сразу (keyframe `pop` из app.css + transition `is-open` из patterns.css, потому что `openModal` навешивает на ту же разметку ekh-классы через `openExistingDialog`, [app.js:997](../apps/ministry/js/app.js)), а закрывается без анимации вовсе: `closeModal()` мгновенно делает `overlayEl().innerHTML = ''` ([app.js:1000](../apps/ministry/js/app.js)), и `openExistingDialog.close()` снимает классы без фазы выхода ([dialog.js:135](../design-system/js/dialog.js)).

| Before | After | Why |
| --- | --- | --- |
| `.overlay { animation: fade … }` и `.modal { animation: pop … }` ([app.css:601](../apps/ministry/app.css), [app.css:616](../apps/ministry/app.css)) поверх transition-системы `.ekh-dialog-backdrop`/`.ekh-dialog` ([patterns.css:55](../design-system/css/patterns.css)) | Удалить keyframes `fade`/`pop` у слоёв; оставить только transition-механизм `is-open` | Два механизма анимируют одно и то же; keyframes нельзя прервать и они не дают выхода. Transition ретаргетится, если пользователь закрыл слой в момент открытия |
| `openExistingDialog.close()`: снял классы → вызвал колбэки, DOM чистится снаружи мгновенно ([dialog.js:135](../design-system/js/dialog.js)) | Повторить паттерн из `openDialog.close` ([dialog.js:72](../design-system/js/dialog.js)): снять `is-open`, подождать `--t-exit` (при reduce — сразу), затем сообщить `onClosed`; вернуть Promise | Выход должен успеть отыграть до удаления узлов |
| `closeModal()`: `overlayEl().innerHTML = ''` в ту же миллисекунду ([app.js:1000](../apps/ministry/js/app.js)) | Чистить DOM в `onClosed` контроллера | Модал уходит (10px вниз, scale .985→, fade), а не исчезает |
| Вход и выход слоя — одна длительность 200 мс | Вход `--t-layer` 200 мс, выход `--t-exit` 160 мс | Асимметрия «система отвечает быстро»: медленнее там, где пользователь смотрит на появление, быстрее там, где он уже всё решил |
| `.drawer { animation: slide-in … }` без выхода ([app.css:644](../apps/ministry/app.css)) | Перевести на transition + `.is-open` (вход и выход через `translateX(100%)`) | В АРМ drawer сейчас не инстанцируется, но класс — общий шаблон; кто скопирует — унаследует правильный паттерн. Выход в ту же сторону = пространственная согласованность |

Замечания:
- Модалка остаётся с `transform-origin: center` — это правильно: она не привязана к триггеру. Стартовый `scale(.985)` тоже правильный («ничто не появляется из ничего», из нулевого масштаба не растём).
- Esc закрывает модал той же анимацией выхода (160 мс — не воспринимается как задержка); фокус на триггер возвращаем сразу, не дожидаясь конца перехода.

Приёмка: ни один диалог в АРМ не исчезает за один кадр; на замедлении 10% (DevTools → Animations) выход виден целиком, без обрезанного хвоста.

## Фаза 2 — тосты уровня Sonner (~0.5–1 день)

Сейчас: вход keyframe `toast-in` ([app.css:681](../apps/ministry/app.css)), выход — инлайновый `el.style.transition = 'opacity .3s'` затуханием на месте ([app.js:1125](../apps/ministry/js/app.js)), соседние тосты после удаления прыгают вверх мгновенно, таймер жизни не останавливается ни при hover, ни при скрытой вкладке.

| Before | After | Why |
| --- | --- | --- |
| `animation: toast-in var(--t-layer) var(--ease)` — keyframe ([app.css:683](../apps/ministry/app.css)) | Transition + класс `.is-in` (навешивается через rAF после вставки) | Тосты приходят пачками; keyframe при быстрых добавлениях стартует с нуля, transition — прерываем и ретаргетируем |
| Выход: fade на месте, инлайн-стилем, 300 мс дефолтным `ease` ([app.js:1125](../apps/ministry/js/app.js)) | Класс `.is-out`: `opacity: 0; transform: translateX(16px)`, `var(--t-exit) var(--ease)` | Уходить туда, откуда пришёл (вправо) — пространственная согласованность. Инлайн-стиль игнорирует reduce-токены и дизайн-систему |
| После `remove()` соседи телепортируются вверх | Схлопывание: обернуть тост в grid-строку и анимировать `grid-template-rows: 1fr → 0fr` + opacity (или FLIP через translateY) | Комбинация «opacity + высота» — то, что делает стопку живой; событие редкое, layout-анимация допустима |
| Таймер: жёсткий `setTimeout(…, 3600)` | Пауза таймера при hover на регион тостов и при `document.hidden`, продолжение после | Тост не должен исчезать под курсором в момент чтения; классика Sonner — «невидимая» обработка краевых случаев |
| Два тостовых механизма в проекте: `design-system/js/toast.js` и локальный `toast()` ([app.js:1117](../apps/ministry/js/app.js)) | В этой фазе полируем локальный (он единственный используется АРМ); заводим тикет на слияние в один компонент дизайн-системы | Не смешивать полировку с рефакторингом; но двойник должен умереть осознанно, а не жить вечно |

Приёмка: отправить «Запрос сведений» → тост въехал справа, при наведении живёт, уходит вправо; выпустить три тоста подряд и закрыть средний — стопка смыкается плавно, ничего не мигает.

## Фаза 3 — нажатие чувствуется (~0.5 дня; сначала решение по §8)

В спеке зафиксировано «Hover/press кнопок: цвет 120ms; **scale не используем**» ([components.css:30](../design-system/css/components.css)), но новые поверхности АРМ уже нарушают её: `.form-row:active { scale(.995) }` ([app.css:2321](../apps/ministry/app.css)), `.mfb-step:active { scale(.985) }` ([app.css:2520](../apps/ministry/app.css)), `.mfb-palette__grid button:active { scale(.98) }` ([app.css:2601](../apps/ministry/app.css)). Дрейф означает: команда сама тянется к тактильности — решение назрело.

**Рекомендация: узаконить scale-press в §8** (диапазон 0.96–0.985, только transform, 140 мс, при reduce — отключён, как уже сделано в [app.css:2427](../apps/ministry/app.css) и [app.css:2713](../apps/ministry/app.css)). Это самый дешёвый способ дать ощущение «интерфейс слышит руку». Альтернатива — откатить три места до цвета; главное — одинаково везде.

| Before | After | Why |
| --- | --- | --- |
| `.btn` transition только цвета ([components.css:26](../design-system/css/components.css)), `:active` меняет только фон | Добавить `transform var(--t-fast) var(--ease)` в transition и `.btn:active { transform: scale(0.97) }` (иконочные `btn--icon` — 0.96) | Мгновенная физическая обратная связь на каждое нажатие; масштаб тонкий, частота высокая — поэтому быстро и без отскока |
| `.btn--danger:hover { filter: brightness(0.94) }`, `:active { … 0.88 }` — filter не входит в transition-список ([components.css:59](../design-system/css/components.css)) | Пары токенов `--red-hover`/`--red-press` по образцу `--blue-hover`/`--blue-press` | Сейчас hover опасной кнопки меняется скачком (свойство не анимируется), плюс filter — это paint на каждый кадр |
| `button.chip:hover { filter: brightness(0.97) }` ([app.css:370](../apps/ministry/app.css)) | Токен-цвет фона + существующий transition background-color | Та же причина: скачок вместо перехода, paint вместо композитинга |
| Reduce-гейты для `:active`-scale расставлены точечно | Один общий блок в media-query для всех press-scale селекторов | Токены обнуляют длительности, но `:active { transform }` без transition всё равно дёрнется — нужен явный `transform: none` |

Приёмка: зажать и отпустить любую кнопку/строку — видно нажатие; в системных настройках включить Reduce Motion — нажатия не двигаются, цветовая обратная связь остаётся.

## Антицели — где мы НЕ анимируем (это тоже вкус)

- **Перерисовки `renderMain()`** — очередь, фильтры, поиск, seg-переключатели: мгновенно. Оператор делает это сотни раз в день; любые fade превратят инструмент в кисель (принцип Raycast: у самого частого действия анимации нет вообще).
- **Клавиатурные действия**: переходы фокуса OTP, Esc-закрытие поповеров — без переходов.
- **Свойства layout**: не анимируем `height`/`width`/`padding`/`font-size` (единственное исключение — схлопывание тостов, оно редкое). Только `transform`, `opacity`, цвета.
- **Переходы между экранами АРМ** — никаких page-transition.
- **Spring/bounce** — нигде.

## Ритуал ревью (обязателен для каждого PR этого плана)

1. **Slow-mo**: DevTools → Animations → 10% на каждый новый переход. Смотреть: не видно ли двух наложенных состояний, верный ли origin, синхронны ли opacity и transform, не срезан ли хвост выхода.
2. **Пересмотр на следующий день** свежим глазом — обязательный второй прогон перед merge.
3. **Reduce Motion прогон** (macOS: Accessibility → Display → Reduce motion): слои появляются и исчезают без движения, но появляются; спиннер остаётся.
4. **Тач-проверка** на планшете: hover-эффекты не залипают.
5. **QA-автоматика**: `npm run lint:design-system` (новые правила Фазы 0) и `npm test`; в visual-тестах Playwright анимации замораживать (`animation-duration: 0`), чтобы снапшоты не флакали.

## Как увидеть и почувствовать разницу — демо-протокол

Два окна: `main` и ветка полировки, `npm run dev`, один и тот же сценарий:

1. **Вход**: кликнуть в поле логина (label уезжает вверх без дрожи текста), ввести неверный пароль (shake), пройти шаги (слайд 8px).
2. **Решение**: открыть заявление → «Запросить сведения» → отправить. До: модал исчезает телепортом. После: модал уходит вниз за 160 мс, тост въезжает справа.
3. **Тост**: навести курсор — живёт, увести — уходит **вправо** (туда, откуда пришёл). Выпустить три подряд — стопка смыкается плавно.
4. **Esc** на открытом модале: уход виден, но не тормозит. Esc на колокольчике: мгновенно.
5. **Колокольчик**: растёт из кнопки, а не из центра экрана.
6. **Нажатия**: зажать строку формы, кнопку решения — интерфейс отвечает рукой.
7. Для приёмки повторить п.2–5 на замедлении 10%.

Критерий «есть разница»: в `main` любое исчезновение слоя происходит за один кадр; в ветке полировки ни одно появление/исчезновение не мгновенно — кроме тех, что мгновенны намеренно (раздел «Антицели»).
